# 样本 · 项目共享上下文（脱敏骨架）

> **注意：这一份是骨架，不是原文。**
> 全局两份文件和 Codex 壳都是原文脱敏（只换名字路径）。这份**不同**——本机真实的 `PROJECT_CONTEXT.md` 有 300+ 行，内含私人项目状态、硬件清单、一串与本机制无关的技术排障记录。整体替换既失真也无价值。
> 所以这里给出的是**七章节骨架 + 每节该写什么 + 真实规模**，你可以据此判断自己那份该长什么样。

---

## 真实规模参考

| 部分 | 本机实际情况 |
|---|---|
| 七个核心章节 | 约前 40 行，项目状态和决策都在这里 |
| 「技术参考」等扩展章节 | 占绝大部分——**这是项目自己的技术文档，不是机制要求** |
| 「变更记录」 | 追加式，一条一行，日期 + 一句摘要 |

**要点**：机制只要求七章节存在且信息归位正确。项目上下文**没有行数上限**——它本来就会越写越厚，厚的部分应该是技术资料，而不是状态流水账。

**判据**：如果你发现「当前状态」章节有 200 行，那是写错了——状态应该随时可读完，历史该进变更记录或专项文档。

## 七章节骨架

```markdown
# <项目名称> · 项目共享上下文

## 项目目标

<要解决的问题、工作范围、预期交付物。两三句话，不要写成愿景宣言。>

## 目录与稳定事实

- 项目根目录：`<绝对路径>`
- 全局共享上下文：`<全局真相源绝对路径>`
- 代码、资料和运行入口：<首次接手时核实后填写>

<这一节回答"东西在哪"。Agent 最需要的就是这个。>

## 当前状态

<已完成 / 进行中 / 阻塞事项。
 每条完成项注明验证日期 + 命令或证据位置。
 没验证过的明确写"未验证"。>

<时效性最强的一节。收尾时最先更新、最该保持可读完。>

## 已确认决策

- <方案 A 已定，理由是 X，确认于 YYYY-MM-DD>
- <约束：不做 Z>

<回答"为什么是这样"。防止下个 Agent 重新讨论已定的事。>

## 下一步

<可执行任务 + 前置条件 + 待确认事项。>

<回答"接着做什么"。没有下一步是危险的信号。>

## 验证方式

<运行、测试或人工验收方法：执行目录、命令、通过条件。>

<共享的验证方法放这里；某端特有的验证边界放该端适配器。>

## 变更记录

- YYYY-MM-DD：<一句摘要>
```

> - 2026-01-05：`export-format.md` 已定字段 `title` / `body` / `created_at`，日期用 ISO 8601，

**已确认决策**

## 三个常见写错的地方

**① 把项目状态写进全局适配器。**
适配器是"这个 Agent 怎么干活"，不是"项目到哪了"。项目状态只有一个位置：本文件。

**② 把「当前状态」写成流水账。**
"今天做了 A，明天做了 B"是变更记录的内容。当前状态要能一眼读完——写**现在是什么样**，不是**怎么变成这样的**。

**③ 把测试结果写成已验证。**
别人跑出来的 `4 passed`，要注明：谁跑的、什么日期、**你本人没有复跑**。写成"已验证"就是造证据。
