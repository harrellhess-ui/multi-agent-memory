# 一种面向本地个人开发者的多 Agent 记忆管理机制

**多 Agent 个人记忆机制**

把一个开发者同时使用的多个编码 Agent（Claude Code / Codex / DSH 等）接到同一套
**落在磁盘上、可读可改可 Git 追踪**的记忆文件上。

日常循环是：记录 → 开工读取 → 工作 → 收尾更新。文件就在本机，不需要服务器或数据库。

Windows 读者建议安装或更新 PowerShell 7，并让 Agent 的终端使用 `pwsh`。安装和版本检查方法见[部署文档第 3 节](记忆机制与部署.md)。

**② 自己读**

| 端 | 提供到什么程度 |
|---|---|
| **Claude** | **完整可复制片段**——全局适配器、项目适配器都是原件，填实即可用 |

## 这套机制靠什么运行

**靠各 Agent harness 自动注入的启动上下文。**

平台运行环境（harness）按自身规则加载原生入口；Agent 再按入口要求读取全局真相源、项目上下文和本端适配器。普通路径引用不会自动展开成文件正文。

| Agent | harness 自动注入什么 | 怎么接上机制 |
|---|---|---|
| Claude Code | `~/.claude/CLAUDE.md` | 内核直接注入它。这个文件本身就是原生入口，再兼全局适配器 |
| Codex | `~/.codex/AGENTS.md` | 自动加载这个壳；壳里的几行指引 Agent 去读 `CODEX.md` |
| DSH | `~/.dsh/AGENTS.md` | 自动加载这个壳；再按配置读 `DSH.md` |

**这套机制就架在这条现成通道上：**

1. 把**启动壳**（`AGENTS.md` 之类）放进 harness 认的那个注入位置；
2. 壳里只写几行——**去读全局真相源 `ME.md`、本项目 `PROJECT_CONTEXT.md`、本端适配器**；
3. 新会话据此读取全局规则和项目状态。

新会话从入口文件读取规则，不依赖模型记住上次对话。

**为什么壳里不直接写规则？** 因为注入入口要尽量薄：平台改了注入行为，你只改壳，规则不用动。

**入口没接上时可能静默失败。**

入口文件名、位置或候选配置不匹配时，新会话可能没有取得预期规则。

未使用约定称呼、不知道项目目标或沿用旧状态时，先核对入口及读取记录，再检查理解和执行是否有误。

开一个全新会话，核对 Agent 实际读取了哪些文件，以及能否从文件给出项目目标和下一步。只回答"读过了"不能作为加载证据。验收步骤见主体文档第 9 节。

> 各 harness 认哪些文件名、要不要额外配置（比如 Codex 的项目适配器需要 fallback 键），
> 见主体文档 [**3.4 接第一个端**](记忆机制与部署.md) —— 那一步接的就是这段话所说的通道。

## 原理一句话

按信息归属保存文件，开工时通过原生入口引导 Agent 读取。

三层，各管各的：

| 层 | 装什么 |
|---|---|
| **全局真相源**（`ME.md`） | 跨项目长期规则、偏好、项目索引 |
| **项目上下文**（`PROJECT_CONTEXT.md`） | 这个项目的目标、事实、状态、决策、下一步 |
| **适配器** | 只有某个 Agent 才需要的操作规则 |

**位置本身就是语义类别**——放全局的就是长期规则，放项目里的就是这个项目的事，
放适配器里的就只对某一个 Agent 有意义。**你不需要给记忆打标签、做检索索引。**

本机制按约定路径读取文件，不提供语义检索。

它和常见的记忆方案（向量检索 / RAG 那一类）的差别，可以这样看：

| | 写入时 | 使用时 | 失败方式 |
|---|---|---|---|
| 语义检索 | 保存供检索的资料 | 按查询召回片段 | 召回不相关或内容过期 |
| **本机制** | 需要人工归位和维护 | 读取约定文件 | **遗漏写入**：下一次会话缺少该信息 |

> **其他方案在问"哪条记忆最相关"；这套机制在问"这条信息该放哪"。**
> 两种做法都需要核对信息是否准确、是否仍然适用。

完整原理（含信息从产生到被用到的完整路径）见主体文档 [**1.1 原理**](记忆机制与部署.md)。

## 这套机制解决什么

- **多个 Agent 各记各的** → 共享一个全局真相源，长期规则只有一份
- **换个 Agent 就断片** → 项目状态落在项目目录的文件里，谁接管都读得到
- **Agent 记的"事实"是错的** → 文件和实时证据是权威，模型自动记忆只是辅助
- **不知道哪条记忆过期了** → 每条信息有唯一归属位置，收尾时按位置核对
- **自己的长期积累会散** → 记录、读取和收尾更新使用同一组本地文件
- **改了什么没人知道** → **把治理文件纳入 Git 后**，改动可追踪、可回看（Git 是可选配置；不建就只有手工备份，没有同等追溯）

## 状态与限制

- 作者长期使用文件分层、启动加载和收尾归位的机制。发行版改为独立的收尾文件，尚未在干净环境中按本文档完成从零部署；"交给 Agent 部署"和"教使用者收尾"两条新路径也没有真实运行记录。
- 作者侧已检查仓库页、raw 单文件和 GitHub 自动 ZIP 下载；读者所在网络及 Agent 后续部署行为未验证。
- 详细证据与局限见[主体文档第 10 节](记忆机制与部署.md)。

```text
1. 复制上面的网址版提示词给 Agent
2. 回答它问你的问题
3. 确认它给的放置计划
4. 按第 8 节学会说"收尾"
```

第五步可先做称呼检查：由使用者选定称呼，再在该端的原生入口中写入“每次回答都称呼我为〈自行设定的称呼〉”。替换占位内容后，新开会话问“请用一句话解释版本控制”，检查回答是否使用所设称呼。之后继续核对项目事实和收尾结果，详见主体第 9 节。
