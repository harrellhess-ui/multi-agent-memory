# 一种面向本地个人开发者的多 Agent 记忆管理机制

**多 Agent 个人记忆机制**

把一个开发者同时使用的多个编码 Agent（Claude Code / Codex / DSH 等）接到同一套
**落在磁盘上、可读可改可 Git 追踪**的记忆文件上。

不是平台、不是网页面板、不需要数据库或额外模型 API。

---

## 三种用法

**① 让 Agent 自己看（就是上面那段，推荐）**

**② 自己读**

打开 `记忆机制与部署.md`。完整自包含：机制说明 → 从零搭建 → 日常使用 →
跨 Agent 交接 → 收尾 → 验收方法。

**三端的材料完整度不一样，别指望都一样：**

| 端 | 提供到什么程度 |
|---|---|
| **Claude** | **完整可复制片段**——全局适配器、项目适配器都是原件，填实即可用 |
| **Codex** | **部分片段 + 配置要点**——全局壳的完整正文有，全局适配器的「专属规则」需你按本端实际写；另有必需的 `config.toml` fallback 配置 |
| **DSH** | **接入结构 + 核验要求**——没有完整原件；给的是该端要确认的加载条件，适配器正文需自己写 |

**以 Claude 为主的读者能直接照抄；只做 Codex / DSH 的读者需要多写一段。** 这是当前的实际情况，不是可以忽略的细节。

**③ 看真实系统长什么样**

`sample-system/` 是作者本机在用的机制，**脱敏后的样本**。
用途是回答"我搭的这个对不对"——对照目录结构、文件职责划分、每份文件的篇幅。

| 文件 | 是什么 | 给谁 |
|---|---|---|
| `记忆机制与部署.md` | **主体文档**。机制说明 + 部署教程 + 收尾说明 + 验收 | Agent 和人都读 |
| `收尾流程.md` | **收尾流程正文（必需）**，部署时复制到固定位置，并在全局文件里写明路径 | Agent 用，人了解 |

**没有技能文件，也不需要。** 收尾是一套流程步骤，靠"一个 Markdown 文件 + 全局文件里一行引用"
接上——不需要技能发现机制、不注册斜杠命令、不随平台版本失效。这是刻意的设计。

## 这套机制靠什么运行

**靠各 Agent harness 自动注入的启动上下文。**

每个编码 Agent（Claude Code / Codex / DSH）在开会话时，**harness 自己会把一两个文件的内容塞进系统提示**——你不需要让 Agent "去读"，是运行时替你读的。

| Agent | harness 自动注入什么 | 怎么接上机制 |
|---|---|---|
| Claude Code | `~/.claude/CLAUDE.md` | 内核直接注入它。这个文件本身就是原生入口，再兼全局适配器 |
| Codex | `~/.codex/AGENTS.md` | 自动加载这个壳；壳里的几行指引 Agent 去读 `CODEX.md` |
| DSH | `~/.dsh/AGENTS.md` | 自动加载这个壳；再按配置读 `DSH.md` |

**这套机制就架在这条现成通道上：**

1. 把**启动壳**（`AGENTS.md` 之类）放进 harness 认的那个注入位置；
2. 壳里只写几行——**去读全局真相源 `ME.md`、本项目 `PROJECT_CONTEXT.md`、本端适配器**；
3. 于是每次开新会话，Agent 都是一副"读过你的铁律和记忆"的状态开始干活。

**所以它不依赖模型"记得"。** Agent 每次新开会话本来什么都不记得，这很正常。它的启动认知来自 harness 注入的那段上下文——记忆是从文件**运进去的，不是从记忆里捞出来的**。

**为什么壳里不直接写规则？** 因为注入入口要尽量薄：平台改了注入行为，你只改壳，规则不用动。

**⚠️ 最要紧的后果：入口一旦没接上，是静默失败。**

如果某个 harness 没注入你的壳、或它认的文件名和你的不一致、或注入的候选清单里没有你那个文件名——**Agent 不会报错，它会安静地什么都没读就开始干活**。

这类"没接上"的典型现象：Agent 不称呼你、不知道项目目标、把旧状态当现状、该收尾时不收尾。**看起来像模型不听话，其实是入口没接上。**

**验证方法只有一个**：开一个全新会话，问它"你启动时读了哪几个文件？"——**答不出来或答错，就是入口没接上**。这也是**第 8.5 节**那个验收动作真正在测的东西。

> 各 harness 认哪些文件名、要不要额外配置（比如 Codex 的项目适配器需要 fallback 键），
> 见主体文档 [**3.4 接第一个端**](记忆机制与部署.md) —— 那一步接的就是这段话所说的通道。

## 原理一句话

**把记忆按"该放哪"分好类，然后每次开工把该读的全量塞进上下文**——让正确的知识因为
"放在该放的位置"而必然被读到，而不是靠搜索去猜哪条相关。

三层，各管各的：

| 层 | 装什么 |
|---|---|
| **全局真相源**（`ME.md`） | 跨项目长期规则、偏好、项目索引 |
| **项目上下文**（`PROJECT_CONTEXT.md`） | 这个项目的目标、事实、状态、决策、下一步 |
| **适配器** | 只有某个 Agent 才需要的操作规则 |

**位置本身就是语义类别**——放全局的就是长期规则，放项目里的就是这个项目的事，
放适配器里的就只对某一个 Agent 有意义。**你不需要给记忆打标签、做检索索引。**

**这套机制里没有"检索"这个动作。没有检索，就没有"检索召回错了"这种失败。**

它和常见的记忆方案（向量检索 / RAG 那一类）的差别，可以这样看：

| | 写入时 | 使用时 | 失败方式 |
|---|---|---|---|
| 语义检索 | 便宜——先存进去 | 贵——每次算相似度、还得赌召回准不准 | **召回错了**：最像的不等于对的，而且你察觉不到 |
| **本机制** | 贵一点——你得放对位置、写精 | 便宜——整份全量注入，不用挑 | **没写进去**：不写就没有，但你自己知道 |

> **其他方案在问"哪条记忆最相关"；这套机制在问"这条信息该放哪"。**
> 前一个问题要用模型算，可能算错；后一个问题用归属规则就能答，答完是确定的。

完整原理（含信息从产生到被用到的完整路径）见主体文档 [**1.1 原理**](记忆机制与部署.md)。

## 这套机制解决什么

- **多个 Agent 各记各的** → 共享一个全局真相源，长期规则只有一份
- **换个 Agent 就断片** → 项目状态落在项目目录的文件里，谁接管都读得到
- **Agent 记的"事实"是错的** → 文件和实时证据是权威，模型自动记忆只是辅助
- **不知道哪条记忆过期了** → 每条信息有唯一归属位置，收尾时按位置核对
- **改了什么没人知道** → **把治理文件纳入 Git 后**，改动可追踪、可回看（Git 是可选配置；不建就只有手工备份，没有同等追溯）

## 状态与限制

- **这套机制是作者长期在用的**：文件分层、启动加载、收尾归位、跨 Agent 交接都在真实项目里跑过。
- **但这份文档本身没有在干净环境里按自己的步骤复跑过**。文档够不够陌生读者一次搭起来，
  作者无法替你保证。
- **"丢给 Agent 自动部署"这条路径（第 0 节）和"教使用者用收尾"（第 8 节）都没有真实运行记录**——
  它们是按这个用法新写的。
- **下载这一步已实测**：仓库页、raw 单文件、GitHub 自动 ZIP 三条路都可达；自动 ZIP 解压后顶层文件夹是
  `multi-agent-memory-main`，**与本页提示词的搜索词一致**，所以 Agent 找得到。但**读者所在网络能否访问
  GitHub、以及 Agent 拿到文件后能否真的走完流程，仍未经验证**。
- **许可**：[MIT](LICENSE)。可以放心使用和再分发。

所以：**照着做的时候，遇到说不通、找不到、行为与描述不符的地方，那不是你不会用，
多半是文档漏了东西。这类问题请回报，比"能不能跑"更有价值。**

## 最短路径

```text
1. 复制上面那段网址版提示词给 Agent（不用下载）
2. 回答它问你的问题
3. 确认它给的放置计划
4. 按第 8 节学会说"收尾"
5. 开一个全新会话，验证它能说出项目目标、决策、下一步和收尾流程文件路径
```

前三步十分钟内能做完。**第四步是关键——新会话答不上来，就是没接好。**

> 唯一的前提是**你的 Agent 能联网**。不能联网就退回本地版：先 clone 或下载 ZIP 解压，再复制本地版提示词。
